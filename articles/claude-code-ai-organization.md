## 「優秀な1人の部下」としての限界

Claude Code を実務で使い始めて最初にやったのは、**優秀な1人の部下として扱う**ことでした。何でも頼める、文脈も覚えている、指示も通る。しばらくはそれで回ります。

回らなくなるのは、仕事が実務の規模になってからです。

- 案件の資料が増えると、**1セッションに文脈が載りきらない**
- 本人が書いて本人が確認するので、**間違いに気づけない**
- セッションが終わると**会話ごと消える**ので、同じ説明を毎回やり直す

これは「1人の部下が優秀かどうか」の話ではなく、**1人でやらせている構造の限界**でした。人間の組織が1人では回らないのと同じ理由で詰まっているなら、**同じ解き方をすればいい**——そう考えて、Claude Code を**役割の異なる複数のAI社員からなる組織**として運用する設定一式を作り、公開しました。

https://github.com/ga1101366h-sudo/ai-org-runbook

CEO役のAIが指示を受け取り、担当部署のサブエージェントに割り振り、**別のサブエージェント（レビュアー役）が第三者チェックをかけ**、結果を部署フォルダへ永続化する。この「分業と品質ゲート」を、`CLAUDE.md` と Markdown ファイルだけで表現したものです。フレームワークでもライブラリでもありません。公開しているのは 40 ファイル、MIT ライセンスです。

### どのくらい動いているか

2026年7月中旬から、本業のSE業務・調査・資料作成・日々の記録に毎日使っています（執筆時点は 2026-08-02）。実運用フォルダの中身は、この時点でこうなっています。

| 項目 | 実測値（2026-08-02 時点） |
|---|---|
| 総ファイル数 | **431ファイル / 合計22MB** |
| 主な形式 | md 319 / py 40 / xlsx 36 / png 18 |
| 部署別（主な内訳） | research 141・engineering 106・reviews 58・secretary 56・ceo 29・pm 18・marketing 13 |
| 増えるペース | 平常時は **1日6〜8ファイル**。タスクが重なると跳ね上がる（7/27〜7/31 の実測：41 / 16 / 42 / 54 / 44） |

ここで**「効率がN倍になった」とは書きません。測っていないからです。** 言えるのは「これだけの成果物が実際に出力され、ファイルとして残っている」という事実だけです。

数字で面白いのは内訳のほうで、**reviews が58ファイル**あります。全体の1割強が「作ったものをチェックした記録」で埋まっている。**組織にした効果が一番出ているのはここ**だと思っています。

なお、この431ファイルの中身は業務情報なので公開していません。公開したのは**構造とルールだけ**（40ファイル）です。

そして、この記事で一番書きたいのは設計の綺麗さではなく、**そこに至るまでに踏んだ地雷のほう**です。リポジトリで一番読む価値があるのも [`docs/02_失敗とルールの履歴.md`](https://github.com/ga1101366h-sudo/ai-org-runbook/blob/main/docs/02_失敗とルールの履歴.md) だと思っています。

### 想定読者

- Claude Code などのAIコーディングエージェントを、遊びではなく**実務**で回している人
- AI駆動開発をチーム／複数エージェントで回したい人
- 「AIを使っています」の中身を具体的に知りたい人

## 3つの壁と、組織で解くという発想

冒頭に挙げた行き詰まりを一般化すると、AIエージェントに実務を任せたときに必ず出る3つになります。

1. **コンテキストが溢れる** … 案件が進むほど関連ファイルが増え、1セッションに載りきらない
2. **もっともらしい嘘が出る** … 一次資料に無いことを、それらしい文章で埋めてくる
3. **記憶が消える** … 会話は次のセッションに引き継がれない。ノウハウが蓄積しない

これは「モデルが賢くなれば消える」問題ではなく、**運用の設計で解く問題**だと考えました。そこで、それぞれに「組織」のメタファーを当てています。

| 壁 | 解き方 | 実装 |
|---|---|---|
| コンテキストが溢れる | **部署ごとにコンテキストを分ける** | `.company/<部署>/CLAUDE.md` に役割とルールを分離 |
| もっともらしい嘘が出る | **作る人とチェックする人を分ける** | エンジニア役 → レビュアー役の品質ゲート＋確度ラベル＋出典必須 |
| 記憶が消える | **会話でなくファイルに書く** | 全作業を担当部署のフォルダに記録。会話は一時記憶と割り切る |

部署は CEO / 秘書 / PM / リサーチ / 開発 / マーケティング / レビュー の7つです。

## 設計の中身

### 1. 部署分割によるコンテキスト分離

ルートの `CLAUDE.md` に**全社共通のルール（憲法）**だけを置き、各部署の `CLAUDE.md` には**その部署固有のルールだけ**を書きます。部署側にはこう書いてあります。

> 確度ラベル【事実】【推測】【提案】【要確認】＋出典・守秘・見やすさは**ルートCLAUDE.md準拠**（ここには再掲しない＝DRY）

理由は単純で、部署ごとに全社ルールを再掲すると、**ルールを1つ変えたときに6ファイル直す羽目になり、必ずどこかが古いまま残る**からです。レビュアー役のチェック観点にも「二重管理を嫌う（DRY）」が入っているので、**自分たちの設定ファイル自体にレビュアーの観点を適用している**格好になります。

### 2. エンジニア役とレビュアー役を分ける品質ゲート

```
オーナー ─指示→ CEO（割り振り）
   ├─▶ 🛠 エンジニア役（サブエージェント）… 実際に作業
   ├─▶ 🔍 レビュアー役（別サブエージェント）… 第三者チェック
   └─▶ CEO … 結果を集約して人間に解説
```

ポイントは「別のサブエージェント」であることです。

**同一セッション内での自己レビューは、自分が書いた文章を自分で肯定する方向に働きます。** コンテキストを共有しない別エージェントに、**成果物と一次資料だけを渡して**チェックさせると、「一次資料に書いていないのに書かれている記述」が実際に検出できるようになりました。

レビュアー役には人格ファイル [`.company/reviews/レビュアー人格.md`](https://github.com/ga1101366h-sudo/ai-org-runbook/blob/main/.company/reviews/レビュアー人格.md) を読み込ませます。これは机上で設計したものではなく、**実際のレビュー会・顧客定例で観察された指摘パターンを、そのつど追記して育てた30項目**です。たとえば：

- 図やフローだけで済ませず、**文字で書かせる**
- 現行資産の**無批判な転記**を排除する（顧客レビューで最も多かった指摘。全体の約1/3を占めた）
- 不整合の**事実は指摘するが、原因は断定しない**
- 判断は示す。ただし**判断の明確さと根拠の確度は別の軸**として書き分ける

### 3. 確度ラベルと出典必須

すべての記述に【事実】【推測】【提案】【要確認】のラベルと出典（資料名＋シート＋行番号／ファイルパス）を付け、レビュアー役が実ファイルを開いて照合します。憲法にはこう書いてあります。

```markdown
## ハルシネーション・推測の防止（最重要・全作業に常時適用）

1. **確度ラベル必須**：各記述に【事実】／【推測】／【提案】／【要確認】を付け、**出典**を併記する
2. **事実と推測を絶対に混ぜない**：一次資料に無いことを【事実】として書かない。
   分からないことは「未確認」と正直に書く。**空欄を埋めたくても捏造しない**
3. **一次資料に当たる**：記憶や推測で答えず、該当ファイルを実際に開いて読んでから書く
4. **ツールの実行結果を捏造しない**：呼び出していないツールの結果・成否・ファイルの存在を、
   地の文で「実行済み」として書かない
```

ただし、運用して分かったのは**ラベルより「実測」の方が効く**ということでした。これは後述します。

## ある1日の実例 — 組織にして何が変わったか

抽象論だけだと「で、実際どう動くの？」が伝わらないので、この記事を書いた日（2026-08-02）に実際に回した1件を書きます。**ある調査タスク**（13件の対象をWebで調べて比較表にまとめる）です。

```
1. オーナーが調査を依頼
     ↓
2. CEO がリサーチ役（サブエージェント）に割り振り
     ↓  13件をWebで調査し、確度ラベルと出典URL付きのレポートを作成
3. レビュアー役が起動 — 全URLを実際に開いて照合
     ↓  ★数値の誤りを発見 → 差し戻し
4. エンジニア役が修正＋Excel化 → 再レビュー
     ↓  ★さらに1件の誤りを発見 → 再修正
5. 最終確認で承認
```

結果、**レビューを2周させたことで、外部サイトの表示を鵜呑みにした数値誤りを2件潰しました。**

とくに2件目が厄介でした。**検索の絞り込み条件がページの表示値そのものを書き換えていた**——つまり、そのページを開いた人には正しい数字に見えるが、条件を外すと違う数字が出る、という類のものです。**普通に人間が目視していたら、まず気づけません。**

ここで書きたいのは「速くなった」ではありません。**1人（1エージェント）では担保できなかった検証密度が出た**、ということです。

- リサーチ役は**13件を調べる**ことに集中していて、自分の出力を疑う余力がない
- レビュアー役は**成果物と一次資料しか渡されていない**ので、調査時の思い込みを引き継がない
- だから「URLを1本ずつ開き直す」という、**同一セッションでは絶対にやらない検算**が実行される

同じモデルです。賢さは変わっていません。**変わったのは、渡す情報と役割を分けたことだけ**です。

逆に言うと、これは**時間がかかります**。サブエージェントは1体ずつ逐次で動かすルールなので、単純な作業ほど「自分でやったほうが速い」局面はあります。そこは後半で正直に書きます。

## 実際にやらかしたこと

ここからが本題です。`CLAUDE.md` が長いのは、設計が緻密だからではなく、**事故のたびに1行ずつ足したから**です。文書化したインシデントは現時点で19件あります。

### 事例1：実行していないツールの結果を「実行済み」として書いた

朝のブリーフィングで、音声読み上げとファイル保存を**実際には実行していないのに**、「再生完了 205616 bytes」「File successfully updated」といった**それらしいログを地の文に書いて「実行済み」と報告**しました。「読み上げがないな」という指摘で発覚し、実ファイルを見たら保存もされていませんでした。

怖いのは、これが**複雑な推論ではなく定型操作で起きる**ことです。実行 → 結果を待つ、という往復を省略して、期待される結果を先に書いてしまう。派生も2つありました。

- **派生A**：ツール結果に紛れたノイズを本物の結果と取り違え、未修正のまま「16箇所修正完了・検索一致なし」と報告。直後の本物の読み込みで11箇所の残存が発覚
- **派生B**：**実在しないユーザー発言を捏造し、それに応答した**。会話ログを実測すると、その文言はユーザー入力として存在しなかった

対策として入れたのがこれです。

> **完了報告の直前に、独立した単純なツール（Grep / ファイル存在確認 / 一覧表示）を1回走らせ、その実結果だけを根拠にする**

確度ラベルより、この1行のほうが明確に効きました。ラベルは「書いた本人の自己申告」ですが、実測は外部からの入力だからです。

### 事例2：古いノートに引きずられて、廃止済みの仕組みを復元した

ある自動化を不具合のため廃止し、最新のメモリにその旨を記録していました。にもかかわらずAIは、**より詳しく書かれていた古い技術ノート**だけを読んで、廃止済みの仕組みを「復元」しました。**古いノートほど実装当時の詳細が書かれていて情報量が多く、引っ張られる**のです。加えて、**メモリの索引の1行だけを見て本文を開いていなかった**。

→ 「索引で済ませず本文を開く」「最新の記述を古いノート・自分の記憶より優先する」をルール化。

### 事例4：帳票テンプレの項目を勝手に作り替え、存在しない項目を捏造した

別セッションのAIが「テンプレートの記述が複数ファイルで食い違っている」ことを問題視し、**帳票の項目構成そのものを書き換えました**。その際、**実物のフォームに存在しない項目を新設**しています。書き換えは5ファイルに及びました。

問題は、**テキストのメモ同士を突き合わせて「正しい姿」を推定したが、実物を一度も見ていない**ことです。「整合性を取る」という善意の作業が、**一次資料から最も遠い成果物**を生みました。

→ 「確立済みの型を勝手に作り替えない」「メモ同士が食い違ったら、どちらも信じずに実物を求める」「他セッション・サブエージェントの診断結果は**申告（未確認）**として扱う」。最後のものは、マルチエージェントをやるなら早めに入れたほうがいいルールだと思っています。

### 事例12：不整合の「原因」を断定して外した

ある仕様書で、項目名が定義側と説明文側で食い違っていました。レビュアー役は「**転記ミスです**」と原因まで断定して報告。しかし実際のレビュー会で作成者は「**既存のデータレイアウトの項目名に合わせています**」と回答し、**意図的な設計判断**でした。

重要なのは、**「項目が揺れている」という事実の指摘自体は当たっていた**ことです。外れたのは原因の断定だけ。

→ 「不整合の事実は指摘してよい。原因は断定しない」。書き方は「AとBで食い違っている（該当箇所つき）。どちらに揃えるかご判断ください」まで。

### 事例13：「AとBどちらがいいですか」を投げすぎて、成果物が完成しなかった

AIが1日に10回近く選択肢を人間に投げ、そのたびに作業が止まりました。人間側の言葉が刺さります。

> いつまでたってもファイルが完成しない。私は完成形を確認したい。完成して目視をして判断をさせてください

厄介なのは、同じ人間が同時に「**あたかも推測を確定のように記載するのは避けたい**」とも言っていたことです。つまり **「判断を示せ」と「推測を断定するな」は衝突しうる**。両立のために作ったのが、レビュアー人格の観点30です。

```
❌ 「AとB、どちらがよいですか」            ← 判断を投げている
❌ 「Aです。原因は転記ミスです」            ← 推測を確定として書いている
⭕ 「Aを推す。根拠は〇〇【事実：出典】。
     ただし△△は未確認で、そこが違えばBになる」  ← 判断は明確／確度は分離
```

要は **「態度は断定してよい。根拠の確度は断定してはいけない」**。そして★**「何が違えば結論が変わるか」を必ず書く**。これが、断定を避けたまま判断を示すための鍵でした。

加えて、**可逆性で判断の強さを変える**ようにしています。戻せること（文言の書き換え・書式調整）は決めて進めて事後報告、戻しにくいこと（構成の変更・確立済みの型の改変・外部への送信）は実行前に確認。この原則から、外部へ提出する作業は**自動でsubmitせず、最後は必ず人間が押す**設計にしています。

### 事例19：ルールを書いても、AIは読み飛ばす

**これが一番大きな学びでした。**

ルールをメモリと設定ファイルに丁寧に書きました。それでもAIは、同じ失敗を1日のうちに複数回起こしました。レビュアー役に遵守監査をさせたところ、こう出ました。

> 根本原因は共通して2つ ——
> **(A) 最新の記録の"本文"を読まずに、古い記録・自分の記憶で動いた**
> **(B) 毎ターン守るべき"振る舞い"の確認を機械化していない**
> 是正はいずれも指摘後で、**AIが自発検知できていない点が最大のリスク**

対策として、**毎ターン機械的に通すチェックリストを憲法の冒頭**に置きました。

```markdown
## 🔴 毎ターン確認事項（最優先チェックリスト）

### A. 毎ターン（応答のたびに必ず）
1. **呼称ルールを守る**
2. **音声読み上げ**は、重要な報告・区切り、またはオーナーが求めたときだけ行う
3. 読み上げ文では**誤読しやすい固有名詞をひらがなで書く**
4. **カタカナ語（専門用語）には毎回注釈を付ける**
5. **CEOから会話の切り上げ・休憩を促さない**
6. サブエージェントは **役割名で呼ぶ**（個人名で呼ばない）

### B. 作業・調査の前に
7. **関連する記憶は索引の1行で済ませず、本文ファイルを開いて読む**
...
```

さらに `UserPromptSubmit` フックで、毎ターンこのリマインダーをコンテキストに注入しています。**それでも完璧ではありません**が、明らかに事故は減りました。

チェックリストは**頻度順**（毎ターン → 作業前 → 成果物作成時）に並べるのがコツです。重要度順にすると、毎ターン見るべき項目が下に埋もれます。

### その他のインシデント（抜粋）

| 何が起きたか | 追加されたルール |
|---|---|
| 「ついでに見つけました」と後出しで指摘を小出しにした | 資料の束を開いたら束ごと通す／未走査範囲は先に宣言する |
| 走査スクリプトの拡張子リストから旧形式が漏れ、数百ファイルを「見たつもり」になった | 走査前に拡張子の網羅を確認する |
| 古い資料だけを見て「廃止ではない」と早合点した（新しい資料には廃止と書かれていた） | 新しい資料から先に当たる |
| 自社が作った資料を相手方の資料と誤認し、「御社の資料がこうなっている」と書きかけた | 引用する前に「誰が作った資料か」を確認する |
| 内部管理用の確度ラベルを、外部提出用の資料にそのまま載せた | ラベルは内部用。外部資料では「（見込み）」等の自然な日本語にする |
| 表計算アプリのプロセスを無差別に終了させ、人間が開いていた別ファイルを巻き込んだ | 自分が起動したPIDのみ終了する |

全19件は [`docs/02_失敗とルールの履歴.md`](https://github.com/ga1101366h-sudo/ai-org-runbook/blob/main/docs/02_失敗とルールの履歴.md) にあります。

### ルールの育て方

回し方はこれだけです。

```
失敗が起きる
  → 人間が指摘する
  → CEOが「なぜ起きたか」を分解する（自分をかばわない）
  → 再発を防ぐ最小のルールに落とす
  → 憲法 or 部署設定 or レビュアー人格に追記する
  → 出典（いつ・何が起きたか）を添えて残す
```

**出典を添えるのが肝心**です。なぜそのルールがあるのか分からないルールは、次に読んだAI（または人間）が勝手に消すか、形骸化します。

## 効かなかった対策・引き返した判断

うまくいった話だけ書くと嘘になるので、引き返したものも。

### 「速度優先」でレビューを省いたら、人間自身がレビュアーになった

一時期「小さな作業ならレビュアー役の別立ては不要」という軽量モードで運用しました。結果、AIはレビュアー役を1体も立てずに成果物を作り続け、**確度ラベルの不揃い／別資料の文言を引用した紐づけ誤り／説明不足／原稿の冗長さを、すべて人間が発見する**事態になりました。

**品質ゲートを飛ばした分のコストは、消えるのではなく人間に回るだけ**でした。レビューを省いて浮いた時間より、手戻りに使った時間のほうが大きかった。→ レビュー必須に戻しました。

### サブエージェントの並列起動をやめた（根拠は記憶しか残っていない）

「同時に複数走らせるとバグる**可能性がある**」という予防的な判断で、**1体ずつ逐次**に変更しました。速度は落ちますが、「時間がかかってよい」と明示的にルールへ書いています。

正直に書くと、**不具合が実際に起きた記録は社内資料に残っていません。** 記憶では「複数エージェントがほぼ同時に報告を投げたとき、CEOが過去のやり取りの回答を急に引っ張ってきた」ような挙動があったのですが、当時のセッションはクリア済みで再現ログがない。**この記述自体、公開後の裏取りで直しています** — ルールの根拠すら、記録しないと消えます。

### 自動化フック（セッション終了時の自動読み上げ）を廃止した

当初はセッション終了フックで自動読み上げしていましたが、**バックグラウンド作業中はフックが発火せず無音**になり、原因究明に時間を溶かしました。読み上げ用の隠しコメントが画面に生表示される事故も。

→ フック方式を廃止し、運用ルール（必要なときにCEOが明示的に実行する）へ切り替え。**確実に動く運用ルール > 動くはずの自動化**、という判断です。

### ルールは振り子する

一度緩めて、失敗して、戻す。この往復自体を記録に残しておかないと、**同じ議論を何度もやることになります**。「軽量モードにして戻した」という経緯まで書き残すのが、地味に効きました。

## まだ解けていないこと

- **ルール文書の肥大化**。増え続けるルールをどこで整理・統合するかの基準がまだありません。今は足す一方です
- **サブエージェントへの指示の質**が成果物の質を大きく左右します。ここはまだ職人芸で、型になっていません
- **逐次実行にしたことで、大きめの作業は素直に時間がかかります**。速度と品質のバランスは案件ごとに手で調整しています
- そして前述のとおり、**毎ターンチェックリストを入れても読み飛ばしはゼロにはなっていません**

## 試し方

```bash
git clone https://github.com/ga1101366h-sudo/ai-org-runbook.git my-company
cd my-company
claude
```

```
.
├─ CLAUDE.md          # 憲法：全社ルール（これが起点）
├─ .claude/
│   ├─ settings.example.json
│   └─ skills/        # /daily-log, /status-report, /web-research など5つ
├─ .company/          # 部署フォルダ（ここに記録が溜まる）
└─ docs/              # 設計思想・失敗の履歴・外部連携の型・セットアップ
```

`sample_` で始まるファイルは、構造を示すために書き起こした**架空のサンプル**です（実データではありません）。実運用の記録は一切含めていません。

**ただし、最初から全部入れないことを強くおすすめします。** ミニマム（秘書＋CEOだけ）から始めて、**失敗するたびにルールを1行ずつ足す**。それがこのリポジトリがたどった道であり、たぶん一番早い道です。ここのルールは特定の人間（＝私）の好みと地雷に最適化されているので、そのまま使ってもたぶん噛み合いません。

## おわりに

「優秀な1人の部下」として使うのをやめて組織にしたことで、何が変わったか。正直に書くと、**速くはなっていません。** 逐次実行なので、単純作業はむしろ遅いです。

変わったのは**アウトプットの量と、そこにかかった検証の密度**でした。431ファイルが実際に残っていて、うち58ファイルが「作ったものをチェックした記録」です。1人でやっていたら、レビューは全部私がやるしかなかった。

そして、このリポジトリで公開しているのは、結局のところ**「AIエージェントの失敗ログと、その対策の履歴」**です。

AIエージェントの失敗は"ランダムなミス"ではなく、いくつかの型に収まります。捏造／古い情報の優先／指示範囲の逸脱／原因の断定／人間への丸投げ。**型が分かればルールで塞げます。** そして塞ぎ方の本質は、たぶんこの3つでした。

1. **ルールは書くだけでは守られない。** 参照される場所（憲法の冒頭）に、機械的に通せる形で置く
2. **品質ゲートを省くと、コストは人間に移動するだけで消えない**
3. **ルールには出典（いつ・何が起きたか）を添える。** 理由の分からないルールは消される
